# Native Wolverine→Wolverine is the supported Wolverine path; frameworks align across services; the MT→W interop bridge is demoted to reference

ADR-0001 shipped the MassTransit→Wolverine interop bridge (`ListenToMassTransitQueue`) as the way a Wolverine service participates in cross-context messaging — a deliberate learning artifact, RabbitMQ-only. This ADR reverses that framing for the Wolverine path: the **supported** Wolverine topology is **native Wolverine→Wolverine over conventional routing**, on equal footing with the existing native MassTransit→MassTransit flow. The interop bridge becomes commented-out reference code (kept, not deleted), all services on a flow must run the **same** framework, and there is no runtime wire-format negotiation. Implementation is pending (a forthcoming PRD); the design was settled in a grilling session captured in [`docs/requirements/native-framework-flows.md`](../requirements/native-framework-flows.md).

## Why native conventional routing, not explicit endpoint names

MT→MT carries no hardcoded exchange names: MassTransit's `ConfigureEndpoints` + type-routed `Publish` derive the topology from the message type by convention. True parity therefore means W→W uses Wolverine's `UseConventionalRouting()`, not hand-named exchanges. The *only* place explicit `Namespace:TypeName` names appear in the system is the interop bridge — and they exist there precisely because the bridge imitates MassTransit's convention. Re-introducing explicit names for native W→W would make it *less* like MT→MT, not more. The shared `PatientCreatedIntegrationEvent` type in `Shared/IntegrationEvents` guarantees the publisher's and listener's convention-derived names match with zero coordination. `UseConventionalRouting()` chains on each transport expression (`UseRabbitMq(...)` / `UseAzureServiceBus(...)`), so it lives in both transport branches of `AddWolverineEventBus`, not the shared block.

## Why framework alignment instead of a wire-format config knob

Cross-framework interop couples a consumer to *which framework sent* a message (its envelope + topology dialect), not just to the contract — so the interop surface grows with framework **pairs**, `O(frameworks²)`. Rather than maintain that, we require all services on a flow to run the same framework: both MassTransit, or both Wolverine. This mirrors ADR-0001's broker-alignment rule ("the broker must match across all services or cross-BC events silently stop flowing"). A richer per-listener wire-format mechanism (a service consuming one event via interop and another natively, simultaneously) was designed during the grill but **deliberately not built** — it is preserved as a reference section in the requirements doc for an eventual multi-framework topology. Wolverine→MassTransit interop is not pursued in any broker.

## Why both services default to MassTransit, fanned out by the AppHost

The framework axis is **unguardable** locally: a service cannot see another service's framework at startup, unlike the broker's self-describing `amqp://` vs `sb://` connection string that ADR-0001's format guard checks. So misalignment cannot fail fast — it silently drops messages. Two mitigations: (1) both services **default to `MassTransit`**, so the out-of-box flow is MT→MT (which works on every broker, including the ASB emulator) — this flips `Billing.WebApi`'s current `?? "Wolverine"` default; without it the default pairing would be MT-publish → Wolverine-native-listen → silent no-flow. (2) The AppHost exposes **one `messaging-framework` parameter** (default `MassTransit`) and injects it into both services via `WithEnvironment(...)`, so a single local knob keeps them aligned and cannot drift. This does not violate ADR-0001's "one mechanism everywhere" principle — services still read the same `MessagingFramework` config key they read in production; the AppHost is merely one config *source* (like user-secrets) supplying an aligned value for local dev, exactly as it already centralises the broker resource.

## Why verification is RabbitMQ-only

WolverineFx 4.12.2 cannot inject a separate admin client for the ASB emulator's port-5300 management plane, so native W→W cannot auto-provision topology on the emulator (RabbitMQ is unaffected; a real Azure namespace removes the limit). This was confirmed empirically (2026-06-04): a build probe showed 4.12.2's `AzureServiceBusTransport` has no `ManagementConnectionString` property. Current WolverineFx adds it (latest 6.4.3), feedable from the AppHost's existing `messaging-admin` string — but reaching it is a major 4→6 upgrade with breaking-change risk across the whole Wolverine surface. MT→MT is verified on RabbitMQ *and* the emulator, so RabbitMQ-only is a conscious, externally-forced step down from MT→MT's coverage — accepted for now, revisited if/when the 4→6 upgrade is taken. Verification must confirm the publisher's exchange and the listener's queue/binding names actually **agree** (inspecting RabbitMQ topology or Wolverine startup logs), since a silent convention-name mismatch is the primary failure mode — not merely that a BillingProfile appeared.

## Status

accepted; implementation pending (forthcoming PRD). Supersedes the Wolverine-path/interop framing of [ADR-0001](0001-message-broker-selection.md) — the broker-seam, two-plane emulator wiring, and broker-alignment decisions in ADR-0001 stand unchanged.
