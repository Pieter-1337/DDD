# Native Wolverine→Wolverine is the supported Wolverine path; frameworks align across services; the MT→W interop bridge is demoted to reference

ADR-0001 shipped the MassTransit→Wolverine interop bridge (`ListenToMassTransitQueue`) as the way a Wolverine service participates in cross-context messaging — a deliberate learning artifact, RabbitMQ-only. This ADR reverses that framing for the Wolverine path: the **supported** Wolverine topology is **native Wolverine→Wolverine over conventional routing**, on equal footing with the existing native MassTransit→MassTransit flow. The interop bridge becomes commented-out reference code (kept, not deleted), all services on a flow must run the **same** framework, and there is no runtime wire-format negotiation. Implementation is pending (a forthcoming PRD); the design was settled in a grilling session captured in [`docs/requirements/native-framework-flows.md`](../requirements/native-framework-flows.md).

## Why native conventional routing, not explicit endpoint names

MT→MT carries no hardcoded exchange names: MassTransit's `ConfigureEndpoints` + type-routed `Publish` derive the topology from the message type by convention. True parity therefore means W→W uses Wolverine's `UseConventionalRouting()`, not hand-named exchanges. The *only* place explicit `Namespace:TypeName` names appear in the system is the interop bridge — and they exist there precisely because the bridge imitates MassTransit's convention. Re-introducing explicit names for native W→W would make it *less* like MT→MT, not more. The shared `PatientCreatedIntegrationEvent` type in `Shared/IntegrationEvents` guarantees the publisher's and listener's convention-derived names match with zero coordination. `UseConventionalRouting()` chains on each transport expression (`UseRabbitMq(...)` / `UseAzureServiceBus(...)`), so it lives in both transport branches of `AddWolverineEventBus`, not the shared block.

## Why framework alignment instead of a wire-format config knob

Cross-framework interop couples a consumer to *which framework sent* a message (its envelope + topology dialect), not just to the contract — so the interop surface grows with framework **pairs**, `O(frameworks²)`. Rather than maintain that, we require all services on a flow to run the same framework: both MassTransit, or both Wolverine. This mirrors ADR-0001's broker-alignment rule ("the broker must match across all services or cross-BC events silently stop flowing"). A richer per-listener wire-format mechanism (a service consuming one event via interop and another natively, simultaneously) was designed during the grill but **deliberately not built** — it is preserved as a reference section in the requirements doc for an eventual multi-framework topology. Wolverine→MassTransit interop is not pursued in any broker.

## Why both services default to MassTransit, fanned out by the AppHost

The framework axis is **unguardable** locally: a service cannot see another service's framework at startup, unlike the broker's self-describing `amqp://` vs `sb://` connection string that ADR-0001's format guard checks. So misalignment cannot fail fast — it silently drops messages. Two mitigations: (1) both services **default to `MassTransit`**, so the out-of-box flow is MT→MT (which works on every broker, including the ASB emulator) — this flips `Billing.WebApi`'s current `?? "Wolverine"` default; without it the default pairing would be MT-publish → Wolverine-native-listen → silent no-flow. (2) The AppHost exposes **one `messaging-framework` parameter** (default `MassTransit`) and injects it into both services via `WithEnvironment(...)`, so a single local knob keeps them aligned and cannot drift. This does not violate ADR-0001's "one mechanism everywhere" principle — services still read the same `MessagingFramework` config key they read in production; the AppHost is merely one config *source* (like user-secrets) supplying an aligned value for local dev.

**Broker fanned out the same way (refines ADR-0001).** The AppHost now also fans the **broker** out: it reads one `messaging-broker` value, provisions that container, **and** injects each service's `MessageBroker` via `WithEnvironment(...)`. Previously it only provisioned the container and left each service to read its own `MessageBroker`, so the container and the services could drift (flipping the AppHost broker alone tripped the alignment guard). ADR-0001 had reasoned against propagating the broker as "a second, local-only mechanism"; that concern was about *production*, and propagation is **local-dev only** (it happens solely when the AppHost launches the services). Production still reads per-service config — so the broker and framework knobs are now symmetric: one AppHost value per axis, fanned to both services locally, per-service config everywhere else.

## Verification covers RabbitMQ and the ASB emulator (WolverineFx 6 upgrade, #28)

Native W→W is now verified end-to-end on **both** RabbitMQ and the **ASB emulator**, matching MT→MT's coverage. The original RabbitMQ-only limit was external: WolverineFx 4.12.2's `AzureServiceBusTransport` had no `ManagementConnectionString` property (confirmed by a build probe on 2026-06-04), so `AutoProvision` could not reach the emulator's port-5300 management plane. Issue #28 took the major **4.12.2 → 6.4.3** upgrade, which adds that property; the Wolverine extension now sets it from the AppHost's existing `messaging-admin` connection string on the emulator path (mirroring the MassTransit two-plane wiring), and the emulator auto-provisions the convention topology. A real Azure namespace never needed the workaround.

Verification confirmed the publisher's destination and the listener's queue/binding names actually **agree** — the convention-derived `IntegrationEvents.Scheduling.PatientCreatedIntegrationEvent` — by observing the message delivered to and processed at that exact endpoint on each broker (a silent convention-name mismatch, the primary failure mode, would have meant non-delivery), and confirming the resulting `BillingProfile` row.

**The 4→6 jump required two runtime fixes the build could not surface** (neither is ASB-specific; both broke RabbitMQ W→W too, and the unit/handler tests missed them because they never boot the Wolverine host):

1. **Roslyn runtime compiler split out of core (GH-2876).** WolverineFx 6 no longer bundles the runtime code generator, so the default `TypeLoadMode.Dynamic` throws `"no IAssemblyGenerator registered"` at host start. Fixed by referencing the **`WolverineFx.RuntimeCompilation`** package, which auto-registers the generator (restores 4.x behaviour; no code change). The production-grade alternative — pre-generated static codegen (`codegen write` + `TypeLoadMode.Static`) — was out of scope for this upgrade.
2. **`ServiceLocationPolicy` default flipped to `NotAllowed`.** Handler codegen now throws `InvalidServiceLocationException` for any dependency it must resolve from the container. Our consumers dispatch through `IMediator`, which resolves its handlers via `IServiceProvider` — exactly that pattern. Fixed by setting `opts.ServiceLocationPolicy = ServiceLocationPolicy.AllowedButWarn`, restoring the 5.x default. Tradeoff: every consumed message logs a one-line service-location warning; accepted as the cost of keeping the MediatR dispatch.

## Status

accepted; implementation pending (forthcoming PRD). Supersedes the Wolverine-path/interop framing of [ADR-0001](0001-message-broker-selection.md) — the broker-seam, two-plane emulator wiring, and broker-alignment decisions in ADR-0001 stand unchanged.
